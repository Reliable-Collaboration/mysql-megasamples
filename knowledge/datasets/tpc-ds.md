# Identity
* Proposed MySQL database: **`tpcds`**; 24 tables with the spec's names (already lower snake_case): fact `store_sales, store_returns, catalog_sales, catalog_returns, web_sales, web_returns, inventory`; dimension `call_center, catalog_page, customer, customer_address, customer_demographics, date_dim, household_demographics, income_band, item, promotion, reason, ship_mode, store, time_dim, warehouse, web_page, web_site`; plus the kit's `dbgen_version` (kept, 1 row, records generator version/date).
* Derived from TPC Benchmark DS; current spec **v4.0.0**, but the only openly buildable generators (tpcds-kit, DuckDB) implement **2.10.0** ([kit](/sources/github-gregrahn-tpcds-kit.md), [DuckDB source](/sources/github-duckdb-tpch-tpcds-extension-source.md)). The V4 changes described on the TPC-DS homepage are pricing-model changes ([homepage](/sources/tpc-ds-homepage.md)); whether dsdgen output changed is an [open question](/questions/tpcds-dsdgen-version-output-identity.md). We describe the database as "derived from TPC-DS (generator 2.10.0)".

# Native format and friendlier forms
dsdgen writes `<table>.dat`, `|`-delimited, **trailing delimiter by default** (`-TERMINATE Y`), dates `YYYY-MM-DD`, time `HH:MM:SS`, NULL as empty field (**Inferred**; see hazard 1). DuckDB export: `COPY t TO 't.dat' (FORMAT csv, DELIMITER '|', HEADER false, NULLSTR '\N')`. DuckDB also publishes pre-generated `.duckdb` files (SF10 2.9 GB … SF300 79.3 GB) — not useful for MySQL and TPC-EULA-derived, ignored.

# Conversion path
**Chosen:** `make gen-tpcds SF=1` runs DuckDB `CALL dsdgen(sf=$SF)`, exports 24 (+1) `.dat` files with `NULLSTR '\N'`, computes `baseline.json`, then MySQL `LOAD DATA LOCAL INFILE ... FIELDS TERMINATED BY '|'` dimensions first (date_dim, time_dim, …, customer), then facts; PKs pre-created; `indexes.sql`, `constraints.sql`, `ANALYZE`. Queries: 99 files generated at build time by tpcds-kit `dsqgen -DIALECT mysql -QUALIFY Y -SCALE 1` using a three-line `mysql.tpl` (`__LIMITC="limit %d"`), then a sed/py patch for the incompatibilities below (or from DuckDB `tpcds_queries()`, same edits). Decision: [tpcds-generator-path](/decisions/tpcds-generator-path.md). Fallback: tpcds-kit `dsdgen -SCALE 1 -TERMINATE N -DIR out` in a builder stage (flex/bison/byacc needed).

# Type-mapping hazards
1. **NULLs**: dsdgen's `.dat` shows NULL as an empty field between pipes; `LOAD DATA` turns an empty field into `''`/0 for non-NULL-typed columns, not NULL (Bexhoma: "MySQL is excluded currently because the treatment of NULL during INSERT is complicated"). Mitigation: DuckDB export with `NULLSTR '\N'` (MySQL reads `\N` as NULL), or the kit path with `SET col = NULLIF(@col,'')` for every nullable column. Verify `SELECT COUNT(*) FROM store_sales WHERE ss_customer_sk IS NULL` > 0 after load.
2. Trailing `|` from dsdgen (`-TERMINATE Y` default): use `-TERMINATE N` or `LINES TERMINATED BY '|\n'`; the kit's own `tests/mysql_setup.sh` just accepts the extra-field warnings.
3. `time` column `dv_create_time` and `t_time` (integer seconds) — direct.
4. `decimal(7,2)` money columns: sums in the 99 queries exceed DECIMAL(7,2); MySQL widens SUM automatically; spec f.3 allows COUNT_BIG-style substitutions.
5. Query incompatibilities in the 99 templates (feature survey in [kit record](/sources/github-gregrahn-tpcds-kit.md); MySQL support verified in the manual):
   | Feature | Templates | MySQL 9.7 | Action |
   |---|---|---|---|
   | `full outer join` | q51, q97 | **unsupported** ([Bexhoma](/sources/bexhoma-docs-tpc-ds.md) confirms) | rewrite as `LEFT JOIN … UNION ALL … RIGHT JOIN … WHERE left IS NULL` (spec 4.2.3.4 b.1 allows vendor join syntax; semantics preserved) |
   | `+ N days` date arithmetic (`cast('2000-01-01' as date) + 60 days`) | 18 (q5, 12, 16, 20, 21, 32, 37, 40, 50, 62, 77, 80, 82, 92, 94, 95, 98, 99) | not MySQL syntax | `+ INTERVAL 60 DAY` (allowed by 4.2.3.4 f.1) |
   | `rollup(a,b)` | 11 | supported as `GROUP BY ROLLUP (a,b)` ([manual](/sources/mysql-refman-9-7-group-by-modifiers.md)) | none (or `WITH ROLLUP`, explicitly allowed by 4.2.3.4 c.4) |
   | `grouping(x)` | 4 (q27, 36, 70, 86) | supported | none |
   | `intersect` / `except` | q8, q14, q38 / q87 | supported since **8.0.31** ([manual](/sources/mysql-refman-8-0-set-operations.md)) | none |
   | window functions (`rank() over`, `sum() over`) | 9 | supported (8.0+) | none |
   | `[_LIMITC]` row limit | 84 | `limit N` | dialect file |
   | `stddev_samp` | 6 | supported ([aggregate functions](/sources/mysql-refman-9-7-aggregate-functions.md)) | none |
   | `substr` | 9 | synonym of SUBSTRING | none |
   | `NULLS FIRST/LAST`, `WITH RECURSIVE` | 0 | n/a | none |
   | NULL sort order / CAST to integer differences | several (Bexhoma) | MySQL sorts NULLs first ASC | compare against `answer_sets/*_NULLS_FIRST.ans` variants where they exist; use DuckDB answers with NULL-aware comparison |
   **Inferred:** remaining templates run unchanged; the first execution task runs all 99 at SF 0.01 and records failures.
6. Column named `d_date` (date_dim) and table `date_dim` are fine (DATE not reserved, [keywords](/sources/mysql-refman-9-7-keywords.md)); no reserved-word clashes among the 24 table names.

# Indexing
* PKs from `tpcds_ri.sql`/spec: single `*_sk` on dimensions; composite on facts: `store_sales (ss_item_sk, ss_ticket_number)`, `store_returns (sr_item_sk, sr_ticket_number)`, `catalog_sales (cs_item_sk, cs_order_number)`, `catalog_returns (cr_item_sk, cr_order_number)`, `web_sales (ws_item_sk, ws_order_number)`, `web_returns (wr_item_sk, wr_order_number)`, `inventory (inv_date_sk, inv_item_sk, inv_warehouse_sk)`; load facts pre-sorted by PK (dsdgen emits by ticket/order number, so an ORDER BY in the DuckDB export is needed — **Inferred** cost: sort of 2.9 M rows, trivial).
* `indexes.sql` (rule 2; the canonical queries filter facts by date and join by `*_sk`): on every fact table the `*_sold_date_sk`/`*_returned_date_sk` column, `*_customer_sk`, `*_item_sk` (non-leading), `*_store_sk`/`*_warehouse_sk`/`*_web_site_sk`; on `customer (c_customer_id)`, `item (i_item_id)`, `date_dim (d_date)`, `date_dim (d_year, d_moy)`, `customer_address (ca_address_id)`.
* `constraints.sql`: the FKs of `tpcds_ri.sql` (about 100; all `*_sk` → dimension PKs); orphan check must report 0 for non-NULL keys.
* Opt-in `indexes-partitioned.sql`: `store_sales PARTITION BY RANGE (ss_sold_date_sk)` by year (date_dim d_date_sk ranges), requires dropping the FKs on that table — offered as the partition-pruning demo named in [indexing strategy](/decisions/indexing-strategy.md).

* Query results: DuckDB `tpcds_answers()` at SF 1 (and 10) for all 99; tpcds-kit `answer_sets/` at the qualification scale for the dsqgen-generated text; comparison numeric with tolerance and NULL-order-insensitive where the kit ships `_NULLS_FIRST/_LAST` variants.
* NULL sanity: `ss_customer_sk IS NULL` count > 0; `dbgen_version` has exactly 1 row with `dv_version = '2.10.0'` (**Inferred** value; verify).
