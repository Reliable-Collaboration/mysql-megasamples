# Question
How are the 24 TPC-DS tables and 99 queries produced for MySQL at a smoke-test size and at SF=1?

# Options considered
1. **DuckDB `tpcds` extension** (`CALL dsdgen(sf, keys=true)` → `COPY … (DELIMITER '|', HEADER false, NULLSTR '\N')` → `LOAD DATA`): fractional SF (the only way to get a ~10 MB smoke dataset), no flex/bison toolchain, answers for SF 1/10, same dsdgen 2.10.0 as the kit. **Chosen for data.**
2. tpcds-kit dsdgen 2.10.0 in a builder stage: integer SF only (minimum 1 GB), deterministic `-RNGSEED`, `-TERMINATE N`; ships `tpcds.sql`, `tpcds_ri.sql`, 99 templates, `dsqgen`, `answer_sets/`, and its own `tests/mysql_setup.sh`. **Chosen for queries (dsqgen) and as the SF=1 cross-check/fallback.**
3. Official TPC-DS_Tools_v4.0.0.zip: registration form; and the open ports are 2.10.0 anyway — used only by a human for the version-identity experiment.
4. DuckDB's pre-generated `.duckdb` datasets (SF10+): wrong size class, still EULA-derived — rejected.

# Evidence
[tpcds-kit record](/tools/tpcds-kit.md) (params.h: SCALE is OPT_INT; TERMINATE default Y; RNGSEED 19620718; dialect files lack mysql; netezza.tpl's `limit %d`), [DuckDB extensions record](/tools/duckdb-tpch-tpcds-extensions.md), [TPC-DS 2.10 spec](/sources/tpc-ds-specification-v2-10-0.md) (SF=1 is the qualification size), [Bexhoma](/sources/bexhoma-docs-tpc-ds.md) (NULL handling on MySQL is the known trap).

# Outcome
Data: option 1; `mysql.tpl` = `define __LIMITA = ""; define __LIMITB = ""; define __LIMITC = "limit %d";` + the `_BEGIN/_END` lines, `dsqgen -DIALECT mysql -QUALIFY Y -SCALE 1`, then a committed patch script applying the rewrites in [the dataset record](/datasets/tpc-ds.md) (FULL OUTER JOIN in q51/q97; `+ N days` → `+ INTERVAL N DAY`). The first execution task loads SF 0.01 via option 1 and SF 1 via both options, verifies NULL counts, and compares all 99 results with `tpcds_answers()`.

# Status
accepted (pending [duckdb-generator-fidelity](/questions/duckdb-generator-fidelity.md))
