# Question
How do we obtain the WideWorldImporters / WideWorldImportersDW data for MySQL when no CSV or script form exists?

# Options considered
1. **Restore `WideWorldImporters-Standard.bak` and `WideWorldImportersDW-Standard.bak` in `mcr.microsoft.com/mssql/server:2022-<CU>` (Developer edition, `ACCEPT_EULA=Y`), export every table with bcp `queryout` (multi-character terminators, `ISNULL` sentinels, `.STAsText()` for geography, hex for varbinary, `_Archive` tables included), load into MySQL, and publish the exported tarball + sha256 as a versioned release asset so routine image builds only download that artifact.** (chosen)
2. Rebuild from the SSDT project + `DataLoadSimulation.PopulateDataToCurrentDate` - non-deterministic ("a degree of randomization is used throughout the code"), needs Visual Studio/SSDT publish and 40+ minutes, and the DW additionally needs SSIS. Rejected.
3. Parse the `.bacpac` directly (zip of model + data) - undocumented format; see [open question](/questions/mssql-bacpac-readable-without-sql-server.md). Only worth pursuing if it lets arm64 builders skip SQL Server.
4. Use the Full .bak - needs Developer/Enterprise features (in-memory filegroup, columnstore); the Developer container supports them, but Standard is simpler to restore and has the same data (inferred).

# Outcome
Option 1. Constraints recorded: amd64 builder; 2 GB RAM; EULA accepted in CI only; proprietary tools never copied into the MySQL image; the export artifact (not the .bak) becomes the build input, with row counts and checksums measured in SQL Server at export time and re-verified in MySQL. Temporal tables become current + `_Archive` pairs, columnstore/RLS/sequences/in-memory dropped or emulated as described in the dataset records. Database names `wideworldimporters`, `wideworldimporters_dw`.
