# Question
How are the ported databases packaged as a PostgreSQL image so that it behaves like the MySQL one:
starts with the data in place, offers the same two accounts, and answers the same registry queries?

# Options considered
1. **A cluster initialised and loaded in a builder stage and copied into the final image** (chosen),
   the same shape as MySQL's baked data directory.
2. Init scripts under `/docker-entrypoint-initdb.d` run at first start -- rejected for the reason
   the MySQL decision rejected them: minutes of loading at every first start, and a container that
   is not ready within the budget.
3. One database with a schema per dataset -- rejected: the MySQL naming convention gives one database
   per dataset, the ports keep the identical table set, and DoltgreSQL maps one database to one Dolt
   repository, which the comparison this corpus exists for needs.

# Evidence
* [Image record](/tools/postgres-docker-official-image.md): `PGDATA`, the entrypoint's skip-initialisation
  branch, the `pg_hba.conf` rule the entrypoint would have appended, the 0700 mode requirement.
* Built and tested for all 21 core datasets on 2026-09-09 (`make image ENGINE=postgres`, `make test-image
  ENGINE=postgres`): 40 checks passed; first start answered a real query in 0.5 s against a 30 s budget;
  the data directory is 2,549 MB across the 21 databases plus `postgres` and `megasamples`; the image is
  3.99 GB (`docker images`).

# Outcome
* **Builder stage** (`engines/postgres/Dockerfile`, bash): `initdb` at the image's own `PGDATA` with
  `--encoding=UTF8 --locale=C.UTF-8` and the superuser password `root`; `host all all all scram-sha-256`
  appended to `pg_hba.conf`; a private server started with bulk-load settings (`fsync=off`,
  `synchronous_commit=off`, `full_page_writes=off`, `wal_level=minimal`); accounts and the registry
  created; each database created `TEMPLATE template0 ENCODING 'UTF8'`, then its `schema.sql`,
  `\\copy` per table with an explicit column list, `indexes.sql`, `constraints.sql`, `ANALYZE` and
  the grants; the registry rows inserted; `pg_ctl -m fast stop`. The final stage is the official image
  plus that cluster (`chmod 700`), the docs and the wrapper entrypoint; the stock `postgresql.conf`
  applies at run time, so none of the load settings ship.
* **Accounts.** `postgres` (superuser, password `root`), `admin` (`LOGIN CREATEDB CREATEROLE`, `ALL`
  on every table and sequence plus `CREATE` on `public`, and default privileges for tables created
  later), `demo` (`SELECT` on every table, `USAGE` on `public`, `CONNECT` on every database).
  `POSTGRES_PASSWORD`, `ADMIN_PASSWORD` and `DEMO_PASSWORD` override the passwords at container
  start: the wrapper starts the server privately with `listen_addresses=''`, runs `ALTER USER`, stops
  it, and hands over to the official entrypoint.
* **Registry.** Database `megasamples`, table `datasets` with MySQL's columns plus `engine` and
  `not_ported` (JSON, the port's dropped list). The landing page, the catalogue's engines column and
  the image test read it.
* **Identity.** Auto-increment keys are `GENERATED BY DEFAULT AS IDENTITY`; after the data is loaded
  every sequence is advanced past the largest key with `setval`, so inserts do not collide.
* **Verification of the image** (`megasamples/engines/postgres/image_test.py`): a real query within
  the budget, no re-initialisation, the registry lists exactly the built datasets, every pinned row
  count, `demo` reads and cannot create, update, delete or drop, `admin` writes, no passwordless login
  role; the password overrides are checked from a second container over the Docker network, because
  the image's own loopback is trusted by `pg_hba`.

# Status
accepted
