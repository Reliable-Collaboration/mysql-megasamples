# Question
Ship the core tier as init scripts in `/docker-entrypoint-initdb.d` (loaded on first start) or as a pre-populated `/var/lib/mysql`?

# Options considered
1. **Pre-populated data directory** (chosen; the entrypoint's "already initialized" branch is verified from source, see [docker multi-stage record](/tools/docker-build-multistage.md)). Startup is seconds; the image-level test "starts within budget" is meaningful; users get identical bytes.
2. Init scripts (`.sql.zst` supported natively by the entrypoint per [README](/sources/docker-library-mysql-readme.md)): image is smaller (compressed SQL ≈ 3–5× smaller than InnoDB pages) but first start takes minutes (Employees alone is ~4 M rows), every user pays the load time, and the anonymous-volume semantics mean a re-created container re-loads. Kept only as the documented fallback if P-03 fails.
3. Both: baked data plus init scripts — rejected: the entrypoint skips init scripts when the datadir is non-empty, so scripts would never run.

# Evidence
* Verified from the entrypoint source: when `$DATADIR/mysql` exists the script sets `DATABASE_ALREADY_EXISTS` and skips initialization, `MYSQL_ROOT_PASSWORD` checks and initdb.d, then `exec mysqld` ([entrypoint](/sources/docker-library-mysql-9-7-docker-entrypoint.md)). BuildKit keeps writes made under a declared VOLUME during the build ([Dockerfile reference](/sources/docker-docs-dockerfile-reference.md)). Users, grants and passwords therefore must be created in the builder stage; runtime password override: `entrypoint-wrapper.sh` writes `ALTER USER` statements for `DEMO_PASSWORD`/`ADMIN_PASSWORD`/`MYSQL_ROOT_PASSWORD` to a temporary file and passes `--init-file` to mysqld before `exec docker-entrypoint.sh` (**Inferred** design; `--init-file` availability is checked at P-02, the mechanism at P-03). Two more things the skipped `docker_setup_db` would have done are therefore done in the builder: creating `root@'%'` (default password `root`, overridable at run time) and loading the time-zone tables with `mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql mysql` so `CONVERT_TZ()` works. The `megasamples.datasets` registry is generated by `scripts/registry.py` from `manifest.yaml`, `downloads/*.meta.json` and each `build/baseline.json`, loaded in the builder after the dumps, and re-run by the loader for every extended dataset it loads; nothing else writes to it.
* Open: first-start cost of the anonymous-volume copy of `/var/lib/mysql` ([multi-stage record](/tools/docker-build-multistage.md), Inferred section).

# P-03 result (2026-09-02, `mysql:9.7.2`, Sakila baked)
**Design A confirmed; no fallback needed.** Measured on the build machine:
* First `docker run` ready (a real `SELECT 1`, not `mysqladmin ping`) in **1.53 s**; restart in **1.27 s**, against a 30 s budget. The anonymous-volume copy of the baked directory is not a material cost at this size.
* The official entrypoint takes the "already initialized" branch: its log shows the start banner and InnoDB init, and never "Initializing database". No `MYSQL_ROOT_PASSWORD` is required.
* `COPY --from=builder --chown=mysql:mysql /var/lib/mysql` preserves ownership: files land as uid/gid `999`, directory `mysql:mysql`, and mysqld opens them.
* Data is exact: actor 200, film 1000, payment 16,044, film_text 1000, 6 triggers; `address_id=8` returns `1566 Inegöl Manor`; `CHECK TABLE` reports OK.
* Size: the baked data directory is **235 MB** with only Sakila in it, of which about 100 MB is the default `innodb_redo_log_capacity` plus doublewrite buffers and the system tablespace. The core image is therefore roughly *base + 200 MB fixed + data*, not base + data; §7 and E-01 must use that shape.

Three defects were found and fixed here rather than during a dataset build:
1. `mysqld --initialize-insecure` leaves **root@localhost with an empty password**, and the entrypoint step that would normally set it never runs on a baked directory, so the image would have shipped with passwordless local root. `00-users.sql` now issues `ALTER USER 'root'@'localhost'`.
2. Because of that, the account script must run **last** in the builder: every command after it has to authenticate, and the plan's original snippet ran it before the redo-log re-enable and the shutdown, which failed the whole stage.
3. The base image is `oraclelinux:9-slim` with `microdnf` only — no `unzip`, no `python3`. Every artifact must reach the builder already extracted by the host pipeline; the builder only runs `mysql`, `mysqlsh` and `mysqladmin`.

# Remaining verification (task P-03 in PLAN.md)
Build a throwaway image whose builder stage runs `mysqld --initialize-insecure`, starts mysqld, loads Sakila, shuts down; final stage copies `/var/lib/mysql`; confirm the official entrypoint detects the existing datadir and starts without re-initializing, and that file ownership (uid 999 `mysql`) survives `COPY --from` with `--chown`.

# Outcome
Option 1 (pre-populated datadir). Option 2 remains the documented fallback if P-03 fails on ownership or startup budget.

# Readiness probe (measured 2026-09-02)
`mysqladmin ping` answers "alive" even when the credentials are wrong or the entrypoint is still setting users up, so it must not be used as the S8 readiness gate. The image test waits for a real statement (`mysql -uroot -p… -N -e 'SELECT 1'`) to succeed; on the probe container that was 1 s after the socket appeared and about 6 s after `docker run`.

# Status
accepted (P-03 measures first-start time and chooses between datadir designs A and B)
